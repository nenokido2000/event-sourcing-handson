## 集約の判定基準

**集約 = それ単体でコマンドを受け取り、独立して状態を変えるもの。
その変更には必ず不変条件が伴う。**

- ① 独立したライフサイクルを持つ ② 自前の不変条件を持つ ③ 単独でコマンドを受ける
- **検査法（拒否テスト）**: その名前で**コマンドを拒否できるか**。
  「引当可能が足りないので引き当てられない」と言える主体だけが集約。
  拒否する権限＝不変条件を守る責任であり、それを持つ場所が境界になる。
- **集約は「もの」ではなく「ものについての残高・約束を守る責任者」**。
  ユニット（商品そのもの）は拒否する根拠を持たない＝集約ではない（数える単位＝`Sku` の世界）。
  この判定は**題材依存**であり、「個体識別するか」という別の問いとセットで
  [H13](../decisions.md#h13-ユニットを個体識別するか) に決着（＝代替可能として扱う。判定が変わる条件も同所）。
  在庫は棚×SKUの残高と「引当可能 ≥ 0」を守る＝集約。
- **因果の向き**: 集約を決めてからルールを探すのではなく、**不変条件が境界を決める**。

### BC と集約は別物（入れ子）
| | BC | 集約 |
|---|---|---|
| 何の境界か | 言葉（モデル）の境界 | トランザクション整合性の境界 |
| コードでの姿 | パッケージ（`inventory` 等） | クラス（`InventoryItem` 等） |
| 個数 | 1つのBCに集約は普通いくつもある | 必ずどれか1つのBCに属す |

BC と集約が同名になるのは正常（BC名は領域の中心概念から取られるため）。
区別は名前ではなく種別語が担う＝「在庫コンテキスト」「在庫集約」。
本PoCが4つとも 1BC = 1集約 に見えるのは学習用に絞り込んだ結果。

## 集約（確定）
不変条件（整合性境界）で括った結果、次の4集約に落ち着く。他集約は**識別子で参照**し、
またぐ整合は**ポリシー/Saga による結果整合**（[`02-process.md`](02-process.md) の P1〜P4）で扱う。

| 集約 | 識別子 | 状態（値オブジェクト） | 不変条件 | ライフサイクル |
|---|---|---|---|---|
| 入荷（`InboundReceipt`） | `ReceiptId` | SKU（`Sku`）・受入量（`Quantity`）・残格納量（`Quantity`） | 格納累計 ≤ 受入量 | 受入 →(検品)→ 格納完了でクローズ |
| **在庫（`InventoryItem`）★コア** | `InventoryItemId = (Sku, LocationId)` | 手持在庫・引当済（各 `Quantity`）・**凍結中**（真偽） | **引当可能 = 手持在庫 − 引当済 ≥ 0**／**凍結中は物理を動かすコマンドを拒否** | 格納で誕生 → 引当/払出/調整で状態遷移 |
| 出荷（`Shipment`） | `ShipmentId` | 明細（SKU・ロケーション・数量）・状態（`ShipmentStatus`） | 出荷は引当済み分のみ・状態は 出荷指示→ピッキング→出荷 | 出荷指示 → ピッキング → 出荷 |
| 棚卸（`Stocktake`） | `StocktakeId` | 対象ロケーション・カウント（実地値）・状態 | カウントは対象ロケーションに限定／全対象を数え終えるまでクローズできない | 開始 → カウント → クローズ |

### 値オブジェクト（原始型の乱用を避ける）
- `Sku`（商品識別）, `LocationId`（倉庫内ロケーション）, `Quantity`（非負整数。加減算と `≥` 比較を持つ）, `ReceiptId` / `ShipmentId` / `StocktakeId`。

## 境界づけられたコンテキスト（BC）とサブドメイン分類

| BC | 主な集約 | サブドメイン分類 | 理由 |
|---|---|---|---|
| **在庫（Inventory）** | 在庫（`InventoryItem`）＋引当ポリシー＋リードモデル | **コア** | 事業の差別化＝**在庫引当（Stock Allocation）**。非自明な集約境界（SKU×ロケーション）と不変条件がここに集中 |
| 入荷（Receiving） | 入荷（`InboundReceipt`） | 支援 | 入荷〜格納。コアに在庫を供給するが差別化要素ではない |
| 出荷（Fulfillment） | 出荷（`Shipment`） | 支援 | 引当を消化して出荷。工程管理が主 |
| 棚卸（Stocktaking） | 棚卸（`Stocktake`） | 支援 | 実地棚卸で帳簿を補正。定期・横断 |
| 受注（Ordering）/ 調達（Procurement） | （外部） | 汎用/外部 | 受注・発注は上流の薄い外部トリガとして扱う（本PoCでは内製しない） |

- **コアサブドメイン = 在庫引当（Stock Allocation）**。ここに設計・テストの投資を集中する（不変条件 引当可能 ≥ 0 の異常系、引当先ロケーション選定 P2）。
- 支援（入荷 Receiving / 出荷 Fulfillment / 棚卸 Stocktaking）は素直に実装。汎用/外部（受注 Ordering / 調達 Procurement）は外部トリガとして最小限。

## CQRS（読み書き分離）
- **書き込み側** = Axon 集約（イベントソース）。真実の源泉はイベントストアのみ。
- **リードモデル（プロジェクション）**（用途別に分ける・非正規化・冪等・再構築可能）:
  - `AvailableStockView`（引当可能在庫ビュー）… SKU×ロケーション別の引当可能数（引当の意思決定 P2 の入力）。
  - `AllocationView` … 引当の一覧（誰が/どの注文にいくつ引当済みか）。出荷・取消の入力。
  - `StockLedgerView` … 全在庫変動の履歴（受入・格納・引当・出荷・調整）。**イベントソーシングの旨味（履歴）**を可視化。
  - `StocktakeVarianceView`（棚卸差異ビュー）… `StockCounted`（実地値）と `StockAdjusted`（差分）を突き合わせた棚卸レポート。
- クエリ側に不変条件・ビジネスルールを置かない（CQS 厳守）。

### 導出値の置き場所（棚卸スライスで得た線引き）
| 導出値 | またぐ範囲 | 誰かの不変条件を守るか | 置き場所 |
|---|---|---|---|
| **引当可能** = 手持在庫 − 引当済 | 1集約の中 | ○（引当可能 ≥ 0） | **集約が持つ** |
| **差異** = 帳簿値 − 実地値 | 集約をまたぐ（在庫 × 棚卸） | ✕ | **リードモデル**（棚卸差異ビュー） |

差異は「新しい事実」ではなく**2つの事実の差**なので、集約イベント（`StockDiscrepancyRecorded`）にはしない。

### ポリシー実装方式（M2/M3の設計判断・棚卸スライスで確定）
- **P1・P2・P3・P4 = 状態を持たない**単発の伝播 → 素直なイベントハンドラ（`@EventHandler` → `CommandGateway`）で足りる。
- **P5 棚卸凍結だけが状態を持つ**（何件凍結済みか・未解凍はどれか）→ **Axon の Saga（Process Manager）はここだけ**。
- 語尾をこれに揃える（状態なし＝`...Policy` / 状態あり＝`...Saga`）。導出は [`02-process.md`](02-process.md) の「4本は単発の伝播、1本だけが Process Manager」。

## パッケージ方針（コード落とし込みの指針・M2/M3で適用）
- BC 単位でパッケージを切る: `inventory` / `receiving` / `fulfillment` / `stocktaking`。BC をまたぐ直接依存を作らない（連携はイベント＋ポリシー）。
- 命名は [`.claude/rules/ddd-ubiquitous-language.md`](../../.claude/rules/ddd-ubiquitous-language.md)：コマンド=命令形、イベント=過去形、集約/値オブジェクト=名詞。
- モジュール配置: 集約/コマンド/イベント= `warehouse-domain`、コマンドハンドラ/Axon設定= `warehouse-command`、プロジェクション/リードモデル/クエリ= `warehouse-query`。

## この段で確定したこと

**決定の理由・却下した選択肢は [`../decisions.md`](../decisions.md)（ADR）が正**——ここには③の段に効いた結果だけを置く。

| 決定 | ③への効き方 |
|---|---|
| [H7](../decisions.md#h7-在庫量が減るタイミング) 在庫はピッキング時に減る | 在庫集約の状態遷移が確定。引当可能は不変なのでコアの不変条件に影響しない |
| [H9](../decisions.md#h9-出荷指示の出所と粒度) 出荷指示は外部トリガ・注文単位 | 受注（Ordering）を内製しない＝コンテキストマップで外部扱い |
| [H10](../decisions.md#h10-棚卸調整の表現) 実地値を渡し差分は在庫集約が出す | **棚卸の責任分界**（棚卸は差異を持たない）と**導出値の置き場所**の線引きが決まった（上記「導出値の置き場所」） |
| [H11](../decisions.md#h11-棚卸中の引当をどこまで許すか) 凍結中も引当は通す（**判断根拠は暫定**） | 在庫集約に足すのは「凍結中は物理を動かすコマンドを拒否」の一文だけ＝**支援の都合がコアに混ざらない**。実装ルールは確定、妥当性判断は実績データ待ち（下記 M3 申し送り） |
| [H8](../decisions.md#h8-検品を独立させるか) 検品は独立させない | 入荷集約の状態遷移が最小になる（M2 戦術設計で決着） |
| [H12](../decisions.md#h12-実地値が引当済を下回る棚卸調整) 調整は通し引当可能の負を許容 | 不変条件の**強制点**が「引当コマンドの受付ゲート」だと精密化された（M2 戦術設計で発見） |

### ③で確定した派生事項
- **棚卸の型**: **循環棚卸（サイクルカウント）・ロケーション1軸**。倉庫はロケーションが商品特性でゾーニングされているため、
  カテゴリ軸を別に持たなくてよい。識別子 `(Sku, LocationId)` とも噛み合う（ロケーション指定で対象集約が一意に決まる）。
- **P4 の正体**: 差異検出ではなく**実情の伝達**。P1（入口）/ P3（出口）/ P4（現実との突き合わせ）が同型になり、
  **在庫集約が受ける入力はすべて外から来た物理的事実**という構造が見えた。

## M3 への申し送り（未決・保留）
- **[H5](../decisions.md#h5-ロケーション間の在庫移動)**: `StockMoved`（ロケーション間移動）を M3+ 改修シナリオとして具体化（P1 と同型の2集約またぎ）。

- **凍結対象の列挙が結果整合**である点（直前に格納された在庫が投影に載らず凍結漏れしうる）。PoCでは許容（→ H11 の「既知のリスク」）。
- **M3+ 改修シナリオ候補（追加）**: 出荷の**バッチ化**（ウェーブ／配送便単位）。既存イベントを書き換えず新集約＋ポリシーを足すだけで実現でき、ESの旨味の実演になる。
- **ATDD 受入シナリオ骨子**（言葉だけ）: 受入→格納→引当→ピッキング→出荷の正常系／過剰引当の拒否／過剰出荷の拒否／
  棚卸調整後の引当可能数の整合／在庫元帳に全履歴が並ぶこと／**棚卸中の凍結（格納・払出は拒否され引当は通る）**／
  **実地値が帳簿値より少ない棚卸で手持在庫が実情へ補正され、棚卸差異ビューに差分が出ること**／
  **実地値が引当済を下回っても調整は通り、以降の新規引当が拒否されること（H12）**。M3 で Gauge Spec 化。
