# 受入仕様（ATDD の外側ループ）

> **この文書群が受入基準の正**。ドメインの言葉だけで「何ができていれば完成か」を書く。
> 型・不変条件・例外の正は [`docs/tactical-design.md`](../docs/tactical-design.md)、
> 決定の理由の正は [`docs/decisions.md`](../docs/decisions.md)。ここには**結果だけ**を書く。

## いまの状態（M2 時点）

**言葉だけが揃っていて、ステップ実装はまだ無い**（[`docs/plan.md`](../docs/plan.md) M2 の成果物）。
Gauge を走らせれば全ステップが未実装で落ちる。**それが正しい状態**——ATDD の外側ループは Red から始まる。
M3 で `warehouse-atdd` にステップ実装を付けて緑にしていく。

置き場を `docs/` ではなく `specs/` にしたのは、**M3 でそのまま Gauge Spec になる形で書くため**
（[H31](../docs/decisions.md#h31-受入シナリオの置き場と粒度)）。

## 実行のかたち（M3 で用意する）

**起動済みのアプリに HTTP で REST を直接コールする**。ブラウザも UI も使わない。

```
Gauge（Markdown Spec）→ ステップ実装（Java）→ Playwright の request API → REST → Spring Boot
```

Playwright を使うのは request API（ブラウザを起動せず HTTP リクエストだけ投げるモード）が目的で、
ブラウザ自動化の機能は使わない。

> **観測用 UI（M3-c）は受入 Spec の対象外**（[H34](../docs/decisions.md#h34-観測用-ui-の位置づけ)）。
> **UI は人が業務の動きを理解するための観測手段**であって、完成の定義ではない。
> ここに UI 操作のシナリオを混ぜると、受入基準に UI の都合が入り込んで Spec が生きたドキュメントでなくなる。

## 何をここに書き、何を書かないか

受入 Spec と内側の TDD（[`docs/tactical-design.md`](../docs/tactical-design.md) の各「テスト骨子」）は
**役割を分ける**。両方に同じことを書くと、遅くて壊れやすいテストが二重管理になる。

| 置く場所 | 書くもの |
|---|---|
| **受入 Spec（`specs/`）** | ①各スライスのハッピーパス ②**コアの不変条件**（引当可能 ≥ 0・凍結中の物理操作）の拒否 ③**集約をまたぐ結果整合**（ポリシー P1〜P6・サーガ P5 が繋がって在庫が動くこと） |
| **Fixture テスト（内側 TDD）** | 例外の網羅（数量ゼロ・二重クローズ・明細に無い引当ID…）、単一集約の受付ゲート、選定規則の場合分け |

線引きの根拠は「**受入 Spec でしか捕まえられないのはポリシーを介して集約がつながる部分**」という一点。
単一集約の受付ゲートは `AggregateTestFixture` のほうが速く正確に書ける。

## ファイル構成

Spec 本体は**題材ごとのサブディレクトリ**に置く（この案内文書を Gauge が Spec として
解析しないようにするため。理由は [`decisions.md`](../docs/decisions.md#h37-受入テストハーネスの版と-gradle-組み込み方) の改訂）。

| ファイル | 対応するスライス | 中身 |
|---|---|---|
| [`warehouse/receiving.spec`](warehouse/receiving.spec) | M3-a | 入荷 → 格納 → 在庫計上（格納伝播 P1） |
| [`warehouse/allocation.spec`](warehouse/allocation.spec) | M3-a ★コア | 受注 → 引当（P2）。**不変条件 引当可能 ≥ 0** |
| [`warehouse/shipping.spec`](warehouse/shipping.spec) | M3-a | 出荷指示 → ピッキング → 払出（出庫反映 P3）→ 出荷／取消 → 引当解放（P6） |
| [`warehouse/stocktaking.spec`](warehouse/stocktaking.spec) | M3-b | 棚卸開始 → 凍結（棚卸凍結 P5）→ カウント → 調整（棚卸反映 P4）→ クローズ → 解凍 |

## 書式

Gauge の Markdown Spec。`# 仕様` / `## シナリオ` / `* ステップ`（引数は `"..."`）。

**太字の行（`**前提**` `**操作**` `**期待**`）は Given-When-Then の見出し**で、Gauge からは
コメントとして扱われる（レポートには出る）。ステップではないので実装は要らない。

```markdown
## 引当可能の範囲で引き当てる

**前提** 棚 A-01 に 50 個ある

* 入荷 "RCP-1" で SKU "SKU-A" を "50" 受け入れる
* 入荷 "RCP-1" から ロケーション "A-01" へ "50" 格納する

**操作** 30 個の注文が入る

* 受注 "ORD-1" の明細 "OL-1" で SKU "SKU-A" を "30" 受け付ける

**期待** 引当可能が 20 に減る

* 引当可能在庫ビューの SKU "SKU-A" ロケーション "A-01" は 手持在庫 "50" 引当済 "30" 引当可能 "20"
```

## ステップ語彙

**この一覧が M3 のステップ実装の設計図**になる。新しい言い回しを増やす前に、既存のステップで
書けないかを先に見る（ステップが増えるほど実装と保守が増える）。

### 操作（コマンド = REST の POST）

| ステップ | 対応するコマンド |
|---|---|
| `入荷 <受入> で SKU <sku> を <数量> 受け入れる` | `ReceiveStock` |
| `入荷 <受入> から ロケーション <棚> へ <数量> 格納する` | `PutAwayStock` |
| `入荷 <受入> を 理由 <理由> でクローズする` | `CloseInboundReceipt` |
| `受注 <注文> の明細 <注文明細> で SKU <sku> を <数量> 受け付ける` | 外部トリガ `OrderAccepted` |
| `受注 <注文> の明細 <注文明細> を取り消す` | 外部トリガ `OrderCancelled`（[H46](../docs/decisions.md#h46-出荷指示前に注文が取り消されたときの引当解放)） |
| `出荷 <出荷> を 注文明細 <注文明細> の引当で指示する` | `RequestShipment`（明細は引当ビューから組み立てる） |
| `出荷 <出荷> の引当 <引当> を <数量> ピッキングする` | `PickStock` |
| `出荷 <出荷> を 完了区分 <区分> で出荷する` | `ShipStock` |
| `出荷 <出荷> を 理由 <理由> で取り消す` | `CancelShipment` |
| `棚卸 <棚卸> を 対象ロケーション <棚の列挙> で開始する` | `StartStocktake` |
| `棚卸 <棚卸> で SKU <sku> ロケーション <棚> を <数量> 数える` | `CountStock` |
| `棚卸 <棚卸> を 理由 <理由> でクローズする` | `CloseStocktake` |

在庫集約のコマンド（`PlaceStock` / `AllocateStock` / `IssueStock` / `DeallocateStock` /
`AdjustStock` / `FreezeStock` / `UnfreezeStock`）に対応するステップは**置かない**。
すべてポリシー・サーガが発行するもので、**外から直接叩けてしまうと受入仕様が実装の裏口を通る**。

### 確認（クエリ = リードモデル照会）

| ステップ | 見るビュー |
|---|---|
| `引当可能在庫ビューの SKU <sku> ロケーション <棚> は 手持在庫 <数量> 引当済 <数量> 引当可能 <数量>` | `AvailableStockView` |
| `引当可能在庫ビューの SKU <sku> ロケーション <棚> は 棚卸中 <真偽>` | 〃 |
| `引当可能在庫ビューに SKU <sku> ロケーション <棚> の行は無い` | 〃 |
| `引当ビューの 注文明細 <注文明細> の引当は <件数> 件` | `AllocationView` |
| `引当ビューの 引当 <引当> は 数量 <数量> 状態 <状態>` | 〃（状態＝引当中／払出済／解除済） |
| `在庫元帳ビューの SKU <sku> ロケーション <棚> には 次の行が この順で並ぶ` ＋ 表 | `StockLedgerView` |
| `棚卸差異ビューの 棚卸 <棚卸> には SKU <sku> ロケーション <棚> が 帳簿値 <数量> 実地値 <数量> 差異 <数量> で並ぶ` | `StocktakeVarianceView` |
| `棚卸干渉ビューには ロケーション <棚> の <コマンド> が <件数> 行 積まれる` | `StocktakeInterferenceView` |

### 拒否の確認

| ステップ | 意味 |
|---|---|
| `直前の要求は <例外> で拒否される` | 同期のコマンド拒否。例外名は [`docs/tactical-design.md`](../docs/tactical-design.md) の**集約ごとの例外一覧**（強整合の受付ゲート）と**前段バリデーション**の表（best effort・[H47](../docs/decisions.md#h47-前段バリデーションの枠組み)）が正。`DuplicateStocktakeException` は後者 |

**ポリシーの中での失敗はこのステップでは観測できない**（要求そのものは受理されている）。
その場合はビューが「そこまでしか動かないこと」で確かめる（例: 在庫が足りない注文の部分引当）。

## 結果整合の扱い

**ビューを見る確認ステップはポーリングして待つ**（タイムアウト付き）。プロジェクションもポリシーも
非同期なので、コマンドの応答が返った時点ではまだ反映されていない。待ち時間を Spec の文面に
書かない（`* 3秒待つ` のようなステップは置かない）——**待ちは実装の都合で、受入基準ではない**。

## タグ

| タグ | 意味 |
|---|---|
| `m3-a` / `m3-b` | [`docs/plan.md`](../docs/plan.md) M3 の刻み（a=入荷〜出荷 / b=棚卸） |
| `harness` | **最初にハーネスを立ち上げるための薄い1本**（plan.md M3 の「薄いハッピーパス1本」）。各 spec に1つだけ |
| `core` | コアサブドメイン（在庫引当）に直接触るシナリオ |
| `invariant` | 不変条件の異常系。**落ちたら設計が壊れている** |

## 既知の観測の穴（M3 で決める）

**入荷・出荷・棚卸の集約には専用のリードモデルが無い**（5種はすべて在庫と棚卸の結果を見るビュー）。
そのため「入荷が全量格納でクローズされた」「出荷が完了した」といった集約側の到達状態は、
**在庫ビューへの波及か、次のコマンドが拒否されることでしか外から確かめられない**。

本骨子はその制約のまま書いてある（外から見える範囲だけで書く、という意味では正しい姿）。
M3 で不足を感じたら、**ビューを増やすのではなく REST に集約の照会を足すか**を先に判断する
（[`.claude/rules/cqrs-projection.md`](../.claude/rules/cqrs-projection.md) の「1つの万能ビューに寄せない」）。
